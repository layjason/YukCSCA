## User-observable outcome

The first platform admin publishes a lesson or remediation unit — the platform's explanation-bearing teaching content — whose explanation-language version offers students an optional reviewed short video: the explanation in playable form, produced from an admin-authored script that compiles to a validated template-bound scene specification with synchronized gTTS narration, or attached as an uploaded finished video. Students play only the Published result with captions/transcript and resume, while the complete TEXT/MATH/IMAGE unit remains the non-blocking baseline.

## Why this slice is the current boundary

The reviewed-video closed loop (author/upload → produce → human review → publish → student play) is one lifecycle over one asset family; splitting off either source path would leave the other without the shared review/publish/playback substrate (D-01). The template-bound scene specification (requirements V1.7) makes production safe without untrusted code execution, and the finished-video upload path is the escape hatch for content the template library cannot express. Adjacent agent-generated video (`US-AGENT-06`) is excluded: it reuses this pipeline later but must not delay the text Q&A slice `VS-011`.

## Capability and adjacent contract horizon

- Owning capability or lifecycle: optional reviewed short-video assets on lesson/remediation units (Draft → human review → Published), including production jobs.
- Closely related stories inspected but not accepted into this slice: `US-AGENT-06` (derived video after a text answer), `US-ADM-06` (flagged-output review; only the value-free audit surface is shared), transcript translation workflows.
- Relevant actors, states, transitions, and invariants included now: admin authoring/upload, render-job lifecycle, review/publish, student playback/resume; watching is not mastery; missing/failed video never blocks publication.
- Deferred transitions and why they remain independently valuable: agent-scripted production needs the `VS-011` AI provider adapter; LLM-assisted script compilation needs the same adapter; additional render templates grow the library without reopening the contract.
- Compatibility/additive-evolution strategy for deferred work: `US-AGENT-06` adds a producer of scene specifications and reuses validation, worker, jobs, storage, and the Draft → review path additively; new templates are registry entries, not contract changes.
- Why a smaller or larger boundary would be worse: upload-only would postpone the primary product value (automatic creation, D-01); adding agent production would couple this slice to unbuilt AI infrastructure.

## In scope

- Admin attaches a bounded finished video per explanation-language version of a lesson/remediation unit, with MIME/container/duration/resolution validation and provenance.
- Admin authors a script (ordered segments: visual action from the reviewed template library + free narration text) that compiles to a schema-validated scene specification; validation errors identify the offending segment (D-04).
- Production pipeline: isolated Python render worker (pinned Manim CE + pinned `manim-voiceover` without the transcribe extra + gTTS + FFmpeg/FFprobe), PostgreSQL-polled job table, bounded retries/timeouts, per-segment and total duration policy.
- Narration and captions: per-explanation-language gTTS synthesis; WebVTT cues derived from segment audio durations; narration text is the authoritative transcript.
- S3-compatible object-storage adapter for video/caption bytes (MinIO in dev/test); metadata, provenance, and job state in PostgreSQL; presigned range-capable playback (D-02).
- Admin reviews the Draft playable result (video, captions/transcript, language version, source record) and publishes; replacement records its own provenance.
- Student plays Published video only: range streaming with resume, captions/transcript, client-side speed, low-bandwidth text alternative and retry; no playable control for Draft/rendering/failed/unpublished video.
- gTTS consolidation: Java `SpeechSynthesisPort` gTTS adapter replaces the Edge adapter for term pronunciation (`zh-CN`), clips re-synthesized on next publish (`ADR-0003`).
- Initial reviewed template library: a small pilot set (at minimum: worked-example steps; concept/definition introduction).

## User flow

1. Admin opens a draft lesson/remediation unit and chooses _Add reviewed video_ for one explanation-language version.
2. Admin either uploads a finished video (validated: MIME signature, container, duration, resolution, size) or writes a script in the segment editor (visual action from the template library + narration text), which compiles to a validated scene specification.
3. Uploaded videos attach as Draft; scripts enqueue a production job the admin watches (queued → rendering → ready/failed with bounded retries); the produced video lands as Draft with generated WebVTT and transcript.
4. Admin reviews the Draft playable result, captions/transcript, language version, and source record; provenance is captured per asset.
5. Admin publishes the unit (or leaves the video in Draft); publication never waits for video.
6. Student opens the lesson, plays the Published video (captions/transcript, speed, resume across reconnects), or sees no playable control while the video is Draft/rendering/failed; the text/formula/image path always remains.
7. Admin replaces a published video; the replacement records its own provenance and passes review again before students see it.

## State model

### Owned states

```text
VideoAssetStatus: AWAITING_VALIDATION -> DRAFT | REJECTED ; DRAFT -> REVIEWED ; REVIEWED -> RETIRED (system-managed on replacement publish)
RenderJobState:   QUEUED -> RUNNING -> SUCCEEDED | FAILED (bounded attempts; terminal)
```

`FAILED` is a render-job state, never an asset status: a failed render creates no asset (the failure lives on the job's `RenderJobError`), and an upload-probe rejection yields `REJECTED`.

### Invariants

- Students can play only assets in `REVIEWED` status that are referenced by the active published revision for that explanation language; every other state yields no playable control.
- Production output always enters `DRAFT` with source `PRODUCED`; nothing auto-publishes. `REVIEWED` is reachable only through the human review operation.
- Missing, failed, or in-production video never blocks publication of a complete text/formula/image unit; non-`REVIEWED` attachments are excluded from the published projection without blocking.
- Each asset (including a replacement) carries its own provenance record.
- A draft video attachment carries at least one of `videoAssetId` and `sceneSpecificationId`; `videoAssetId` is the sole publish/projection reference, and the spec id is retained through review so the script stays reopenable (CR-03).
- Captions are editable only on `UPLOADED` assets in `DRAFT`; `REVIEWED` and `RETIRED` are immutable, and caption corrections go through the replacement flow with their own review (CR-09).
- Content progress stores at most one video playback position per resource; each write replaces it, so clients resend the current position on every `IN_PROGRESS` write (CR-02).
- The worker consumes only schema-validated scene specifications; authored or model-generated input takes the same validation.
- Watching or completing a video writes content progress only, never mastery evidence.

### Concurrency, retry, and stale-state rules

- Idempotency boundary: a job renders one scene-specification version; re-enqueue creates a new job, never resumes mid-render.
- Optimistic/stale update behavior: publishing a revision while a job renders leaves the job finishing into Draft against the superseded draft; the admin re-enqueues on the new draft.
- Duplicate event/callback behavior: workers claim jobs via `FOR UPDATE SKIP LOCKED` on the polled table (visibility timeout); duplicate completions are no-ops.

### Contract decisions

- Cookie/token behavior: unchanged bearer access tokens; presigned playback grants are short-lived, returned in a 200 JSON body (never a redirect, CR-01), and never bearer-substitutable — the bearer token reaches only YukCSCA API endpoints, never storage.
- Error codes and problem details: per-segment validation body for scene specifications with a documented path grammar (`segments[i]`, `segments[i].templateActionId`, `segments[i].params.<paramId>`, `segments[i].narrationText`, plus collection-level `segments`/`explanationLanguage`); distinct 409 codes per case — `SLOT_PENDING`, `SLOT_EXPIRED`, `RENDER_JOB_ACTIVE` (with embedded job), `VIDEO_NOT_PLAYABLE`, `CAPTIONS_DERIVED_FROM_NARRATION`, `CAPTIONS_IMMUTABLE`, `CAPTIONS_NOT_EDITABLE`, `REVIEW_PRECONDITION_UNMET`; progress-position violations `INVALID_VIDEO_ASSET` and `POSITION_OUT_OF_RANGE`.
- Pagination/filtering if applicable: none new.
- Compatibility or migration impact: additive operations on admin draft and student academic reads; the only pre-existing operations touched are the two student progress upserts (additive optional field plus a compatible `IN_PROGRESS` relaxation, CR-02).
- Deployment consequences recorded by this slice (not yet active anywhere): CSP `media-src` must include the object-storage origin for presigned playback (CR-01); the storage bucket must allow the web origin for the presigned upload PUT (CORS preflight plus exposed `ETag`) (CR-06).
- Transcript delivery: client-side WebVTT cue extraction is the single transcript mechanism; there is no transcript endpoint (CR-07e). No poster artwork in the pilot — players show the asset's first frame via `preload="metadata"` (CR-07i).

## Backend plan

- Module and package ownership: `academic` module owns assets, scene specifications, render jobs, playback projections, and the storage port; the Python worker is academic-owned infrastructure.
- Application use cases and transaction boundaries: attach/confirm upload (slot-to-asset link persisted at first confirm so replay is idempotent, including replay after slot expiry — `SLOT_EXPIRED` applies only to a first confirm after expiry, CR-08); compile+validate script (stamping the validated `registryVersion`, CR-05); enqueue job (transactional with draft update; 409 embeds the active job); publish (existing validation extended with video state); student playback projection.
- Domain rules: duration/size bounds; template-action whitelist per template registry version; caption/transcript presence before publish of a video-bearing unit; provenance completeness; draft-save video-attachment rules — at-least-one of `videoAssetId`/`sceneSpecificationId`, one attachment per explanation language, language equal to the referenced asset's and spec's `explanationLanguage` (CR-03/CR-07c); captions editable only on `UPLOADED`+`DRAFT` assets (CR-09); progress writes validate `videoAssetId` against the currently published asset and `positionSeconds` against its duration, while reads clamp to the published duration (CR-02).
- Ports/adapters: `MediaStoragePort` (S3-compatible adapter; MinIO dev/test), `SpeechSynthesisPort` (gTTS adapter replacing Edge), worker invocation via the polled job table only.
- Flyway migration: video asset + provenance tables, render-job table, content-progress playback position, template-registry version table (append-only).
- Scheduled/async behavior: worker polls with visibility timeout; bounded retries; terminal-failure surfacing; no scheduler inside Java beyond job claiming helpers.
- Concurrency: workers claim jobs with `FOR UPDATE SKIP LOCKED` on the polled job table, so multiple worker processes never block each other or double-claim; duplicate completions are no-ops.
- Delivery posture (deliberately simple): progressive MP4 muxed with `-movflags +faststart` (moov atom first) over presigned range GETs; published assets are immutable per revision and carry long-lived `Cache-Control` with `ETag`, so browser/proxy caching needs no invalidation logic; no HLS/DASH segmentation and no CDN for the pilot.

## Frontend plan

Completed by the frontend owner 2026-08-22 against `VS-010B-R3-initial`, amplified after two external reviewer passes, and re-verified against the amended `VS-010B-R4-initial` (all nine dispositions confirmed in the contract and generated types). Implementation starts only after `CONTRACT_READY` from the accepted checkpoint. Surfaces extend the existing VS-005 admin editor and VS-008 lesson reader: no new student route, and admin video authoring stays inside `admin-package-detail` (`features/academic-admin`), so the route manifest is expected to remain unchanged.

Durability protocol (the reload-safety backbone; requires CR-03's attachment shape): the draft is saved immediately after `createSceneSpecification` (spec handle), after `createRenderJob`, after `confirmVideoUpload` (asset id saved while still `AWAITING_VALIDATION`), and again when a render reaches `SUCCEEDED` (asset id added beside the retained spec id), so every in-flight id is recoverable from `getAcademicPackage` alone.

### Admin surface (`features/academic-admin`, inside the resource editor)

- Per-resource video panel listing one optional attachment per explanation language from `StudyResource.videos`; each entry resolves status/source via `getAcademicVideo` (`AWAITING_VALIDATION` → `DRAFT` → `REVIEWED`; `REJECTED` with reasons; a failed render creates no asset and surfaces on the embedded job) or, while producing, the embedded spec/job state (CR-03). Produced attachments retain the spec id after success so the script stays reopenable (`replaceSceneSpecification`, transcript from segments, re-enqueue). Attach/remove edits flow through the existing `saveAcademicPackageDraft` `expectedDraftRevision` optimistic-lock path with 409 → reload.
- Upload flow: client pre-checks (MP4, size bound from CR-06 `maxByteSize`) → `createVideoUploadSlot` → direct `PUT` to `uploadUrl` (no bearer to storage; progress, retry) → `confirmVideoUpload(provenance)` → save the asset id on the draft immediately → poll `getAcademicVideo` until `DRAFT` or `REJECTED`, rendering probe `violations` inline. Mirrors the existing `ImageUploader` provenance/dropzone patterns. (Polling alone was never sufficient for reload recovery — the draft save is what makes the asset durable.)
- Script editor: `listSceneTemplates` drives the action picker and structured param inputs (requires CR-05 descriptors; a raw JSON textarea is not acceptable for AC-02/AC-03 error UX); `createSceneSpecification`/`replaceSceneSpecification` with per-segment inline errors mapped from violation paths (grammar per CR-07); `createRenderJob` with 409 active-job handling; job state polled (`QUEUED`/`RUNNING`/`SUCCEEDED`/`FAILED`, attempts, error code, interval per CR-07) with honest waiting states, stale-snapshot detection (`job.createdAt` vs `spec.updatedAt`, CR-07) and re-enqueue after terminal failure. Reload-safe rediscovery of script and job depends on CR-03's draft handle.
- Draft review (AC-01): review player via the play response (shape per CR-01), captions viewer plus `putAcademicVideoCaptions` for `DRAFT`-status `UPLOADED` assets with VTT validation errors mapped (frozen at `REVIEWED` per CR-09), provenance display, `reviewAcademicVideo` with 409-precondition copy, `REVIEWED` badge. Replacement (AC-09) is a new upload/render plus attachment swap; the old asset retires at publish.

### Student surface (`features/learn`, lesson + remediation readers)

- A `LessonVideo` region renders only when the detail projection's `video` ref is non-null for the requested explanation language (AC-05): fetch the play URL with the bearer token (CR-01 shape) → assign to `<video controls playsinline preload="metadata">` — no autoplay, no `crossorigin` — so native controls provide Range streaming and scrubbing; a custom localized speed menu (0.75/1/1.25/1.5) drives `playbackRate`.
- Captions/transcript (AC-06): fetch WebVTT with the bearer token → blob URL → native `<track kind="captions">`; transcript panel parsed from cues (narration text is authoritative). Captions are offered by default; the toggle follows interface language while caption content follows the asset's explanation language.
- Resume (AC-07, requires CR-02): restore from the content-progress video position clamped to `durationSeconds`; periodic and pause/visibility-change writes ride the existing `upsertContentProgress` coalescer as `IN_PROGRESS` — playback alone never writes `CONTENT_COMPLETE` or any mastery state (AC-12).
- Low bandwidth and failure (AC-08): the TEXT/MATH/IMAGE unit remains the primary alternative and is never replaced by the player; play/captions failures show an actionable in-region retry with expiry-aware refresh (`expiresAt` per CR-01); media errors never render as fake progress or completion.
- Language independence: the ref is per requested explanation language; switching language reloads the ref and never substitutes another language's video.

### Adapters, localization, tests

- Adapters follow the existing per-feature `fetch` + `authorizationHeaders()` style with generated-type re-exports; DEV fallbacks stay inside the safe predicate (never mask 400/403/404/409/5xx or contract mismatches) and fixtures never imply durable review/publication. The asset/job poller is new — no existing poll helper to reuse.
- Localization keys `admin.academic.video*` and `learn.lesson.video*` in id/en/zh-CN (parity-enforced), including aria-labels, live-region text, and error copy.
- Tests: co-located component tests per state (success plus validation/failure/accessibility/edge), adapter tests including fallback isolation and proof `5xx` never becomes mock success, and a `vs010b` Playwright spec proving reload/resume persistence semantics (the follow-up `GET` returns the saved authoritative position after `PUT`), wrong-role/signed-out isolation, and the absent-player state; screenshots under `output/playwright/vs010b-review/`.
- Deployment consequences once CR-01/CR-06 land: CSP `media-src` gains the storage origin for presigned playback; the storage bucket allows the web origin for presigned `PUT` (plus exposed `ETag`).

## Experience and interaction plan

Built against root `DESIGN.md` flow grammar (Orient → Act → Acknowledge → Wait honestly → Resolve → Recover) and `docs/design/README.md`.

- The "no playable control while Draft/rendering/failed/unpublished" rule is absolute: absence renders nothing, never a disabled teaser (AC-05). The text/formula/image unit is the always-present baseline and the primary accessibility and low-bandwidth posture; the video is an optional layer above it, and no viewing state ever uses mastery language (AC-12).
- Student player sits on the white reading surface inside the existing lesson flow — full-width below 600px, bounded column at ≥960px; no new pastel region for video. Native `controls` handle transport; the speed menu and the transcript disclosure are quiet secondary controls (Lucide icons with localized `aria-label`); the dominant action in the region remains the existing lesson continuation, not the player.
- Honest waiting: the player area shows a skeleton only when a `video` ref exists; the job panel shows real state and attempts, never fabricated progress; upload shows byte progress with retry. Failures are actionable, preserve entered script text and provenance fields, and use in-region `feedback-*` tones; toasts remain background acknowledgements per the existing admin pattern.
- Accessibility: native `<video controls>` (keyboard-operable), captions offered by default with a visible toggle, transcript as a text alternative, `role="status"`/live-region announcements for ready/error/resumed transitions, focus recovery after failures, and reduced-motion honored — the only planned motion is the existing resume highlight pulse, disabled under `prefers-reduced-motion`.
- Language independence: player chrome follows interface language; narration and captions follow the asset's explanation language; the exam-language dimension is untouched. Copy is verified in id/en/zh-CN with long-content cases (Chinese narration lengths, speed-menu labels, VTT cue text in the transcript).

## Authorization, privacy, and safety

- Actor authorization: admin-only authoring/upload/enqueue/review; students read Published assets of packages they can access; no parent surfaces.
- Field-level/minimum-data response: jobs and assets expose no student data; playback positions remain per-student private state.
- Minor/guardian consequence: no new personal data collection; video content is reviewed platform content.
